# Luna World — Development Rules

## 1. Общий принцип

Разработка идёт короткими вертикальными шагами: каждая крупная подсистема должна как можно раньше работать в реальном Roblox runtime и multiplayer-контексте.

Не строим большую абстрактную платформу «на будущее» до появления подтверждённой необходимости.

## 2. Git workflow

`main` — основная интеграционная ветка проекта.

Для функциональных изменений предпочтительны короткоживущие ветки:

- `feature/<name>`;
- `fix/<name>`;
- `refactor/<name>`;
- `docs/<name>`.

Крупная функциональность не должна смешиваться с масштабным рефакторингом в одном изменении, если их можно разделить.

Коммиты должны объяснять цель изменения, а не только перечислять файлы.

После merge/supersede задачи:

- соответствующий PR закрывается или merge-ится;
- выполненный issue закрывается;
- superseded issue/PR получает короткий комментарий со ссылкой/объяснением нового baseline;
- short-lived remote branch удаляется после того, как больше не нужна для rollback/review;
- исторические stacked branches не должны оставаться активным рабочим контуром.

## 3. Source of truth

Git — source of truth для:

- кода;
- configuration/definitions;
- тестов;
- документации;
- dev-tool configuration.

Если Rojo-managed script временно изменён в Studio для эксперимента, изменение должно быть перенесено обратно в Git source до завершения задачи.

## 4. Code boundaries

Каждый module/service должен иметь одну ясную ответственность.

Не создавать универсальный `GameManager`.

Если модуль начинает одновременно:

- хранить player data;
- считать combat;
- выдавать loot;
- управлять quests;
- рисовать UI;

границы архитектуры нарушены.

Не вводится жёсткий лимит строк на файл: критерием является количество ответственностей и связность.

## 5. Data-driven design

Баланс и контент по возможности описываются definitions/config:

- items;
- mobs;
- skills;
- quests;
- classes;
- progression curves.

Одинаковые значения не дублируются в нескольких местах.

Изменение display name не должно ломать persistence.

## 6. Network safety

Любой client request считается недоверенным.

Server handler обязан проверять применимые условия:

- типы и форму данных;
- существование entity;
- ownership;
- состояние игрока;
- range;
- cooldown;
- resource cost;
- rate / spam;
- контекст party/dungeon.

Нельзя принимать от клиента готовые значения reward/damage/currency.

## 7. Persistence safety

Изменения структуры сохранений выполняются только с обновлением migration logic и tests.

Запрещено:

- молча стирать неизвестные поля при загрузке старого профиля;
- считать любую ошибку DataStore новым игроком;
- менять meaning существующего persistent ID без migration;
- сохранять runtime Instance напрямую.

## 8. Definition of Done для задачи

Функциональная задача не считается завершённой только потому, что код написан.

Нужно минимум:

1. код соответствует архитектуре;
2. relevant tests проходят;
3. ручной runtime-check выполнен там, где unit test недостаточен;
4. документация обновлена, если поведение/контракт изменился;
5. нет известных критических ошибок в основном сценарии;
6. debug/temp code удалён или явно оформлен как осознанный инструмент.

## 9. Refactoring gates

После каждого крупного milestone проводится отдельная стабилизационная фаза **до начала следующего большого feature block**.

Порядок:

1. зафиксировать рабочее поведение тестами;
2. устранить текущие regressions;
3. удалить мёртвый код и временные обходы;
4. убрать дублирование;
5. проверить границы modules/services;
6. проверить network validation;
7. проверить lifecycle/cleanup;
8. проверить persistence migrations;
9. обновить docs;
10. только после этого начинать следующий milestone.

Цель рефакторинга между milestone — не «переписать всё красиво», а сохранить проект понятным и дешёвым для следующего изменения.

## 10. Refactor rules

Рефакторинг по определению не должен незаметно менять gameplay behavior.

Если требуется одновременно изменить behavior и structure:

- сначала закрепить старое поведение тестами;
- отделить structural change;
- затем изменить behavior отдельным понятным шагом, если возможно.

Нельзя выполнять большой rewrite без конкретной проблемы, которую он решает.

## 11. Dependencies

Сторонняя библиотека добавляется только если:

- она решает реальную проблему;
- выгода выше стоимости зависимости;
- понятны maintenance/security implications;
- она совместима с Roblox/Rojo toolchain.

Для небольшой функции предпочтителен собственный прозрачный код, если он существенно проще зависимости.

## 12. Debugging

Исправление bug начинается с воспроизводимого сценария.

Желательный порядок:

`reproduce → isolate → test/regression case → fix → verify`

Не делать серию случайных изменений «пока не заработает» без понимания причины.

## 13. Документация

Если решение меняет одно из следующего, docs обновляются в той же работе:

- архитектурный контракт;
- persistent schema;
- gameplay rule;
- scope v0.1;
- build/tool workflow;
- versioning/release process.

Архитектурные решения, противоречащие текущей документации, сначала должны быть явно согласованы.

## 14. Product scope protection

Любой хороший feature всё равно может быть неправильным для текущего milestone.

Перед реализацией новой идеи проверяется:

1. нужна ли она для Definition of Done текущей версии;
2. подтверждает ли она core hypothesis;
3. создаёт ли она новые systems/dependencies;
4. можно ли безопасно отложить её на следующую версию.

По умолчанию v0.1 защищается от scope creep.
